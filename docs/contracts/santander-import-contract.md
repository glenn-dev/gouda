# Santander import contract

## Status: v0.1 — frozen baseline

This contract is the approved Santander parser baseline. It is validated against
three monthly private Santander source samples and the 29-test synthetic XLSX
suite. Frozen means that the current behavior is intentional and future source
variants require an explicit contract revision; it does not mean that every
Santander export variant is supported.

## Purpose and boundary

This contract defines the boundary from a Santander XLSX source to Gouda's
raw, validated, and normalized representations. The current implementation is
an isolated Python parser; the contract is not a PostgreSQL schema, Django
model, or migration.

The source observation is documented in
[the Santander source note](../sources/santander-current-account-xlsx.md).
The three product layers remain distinct:

1. the original source artifact;
2. the importer's immutable interpretation;
3. the normalized movement and later user corrections.

PostgreSQL is the confirmed future persistence technology per
[ADR-0002](../decisions/ADR-0002-initial-technology-stack.md). Its physical
schema must wait until this contract and required queries have implementation
evidence.

The XLSX decoding dependency is `openpyxl`, declared in `requirements.txt`.
This is intentional: Gouda owns Santander recognition and financial semantics,
not a partial reimplementation of OOXML package, relationship, style, date,
and cell decoding. The adapter converts openpyxl worksheets to neutral cell and
row snapshots before Santander interpretation begins.

## Contract layers

The `SourceArtifact` and `ImportBatch` tables below describe the future
artifact/import boundary and its persistence projection. They do not claim
that the current pure-Python parser creates those identifiers or exposes every
batch field. In the current implementation, `ParseResult` provides the
workbook-local sheet identity, period, row results/counts, normalized
movements, and reconciliation status; artifact and batch identity remain
unavailable by design.

### SourceArtifact

One private XLSX file as received. The parser may read it but must not modify
it. Artifact retention and import-batch identity are future boundaries; the
current in-memory parser does not create or persist `artifact_id`,
`content_digest`, `batch_id`, or `received_at`.

| Field | Logical type | Nullability | Origin and semantics | Validation | Raw / dedupe / reconciliation |
| --- | --- | --- | --- | --- | --- |
| `artifact_id` | opaque internal identifier | required | Generated by Gouda; identifies the received file | unique within Gouda | no / yes / no |
| `source_kind` | enum | required | Constant `santander_current_account_xlsx` | exact value | no / yes / no |
| `original_filename` | sensitive string | required | Filesystem metadata | retain only in private raw metadata; never log | yes / no / no |
| `content_digest` | opaque digest | required | Byte content of the artifact | stable for the artifact; protect from public output | yes / yes / no |
| `received_at` | timestamp | required | Ingestion environment | timezone-aware | yes / no / no |

`content_digest` remains a future persistence concern and must not be created by
the parser or copied into public fixtures or reports.

### ImportBatch

One attempt to interpret one artifact.

| Field | Logical type | Nullability | Origin and semantics | Validation | Raw / dedupe / reconciliation |
| --- | --- | --- | --- | --- | --- |
| `batch_id` | opaque internal identifier | required | Generated per import attempt | unique | no / yes / no |
| `artifact_id` | opaque reference | required | Links to `SourceArtifact` | must exist | yes / yes / no |
| `parser_version` | version string | required | Parser contract/version used | non-empty, immutable for a run | yes / no / no |
| `sheet_alias` | sanitized string | required | Internal alias such as `S1`; never rely on provider sheet name | stable within artifact | yes / no / no |
| `status` | enum | required | Batch result | accepted, partial, rejected, fatal | yes / no / yes |
| `counts` | structured counters | required | accepted, ignored, rejected, and pending rows | non-negative; sums explain result | yes / no / no |
| `reconciliation_result` | enum | required in parse result | `RECONCILED`, `NOT_RECONCILED`, `INSUFFICIENT_DATA`, or `NOT_APPLICABLE` | explicit independent batch result | yes / no / yes |

### RawRecord

One immutable row interpretation. It preserves what the importer saw without
claiming that the row is a valid movement.

| Field | Logical type | Nullability | Origin and semantics | Validation | Raw / dedupe / reconciliation |
| --- | --- | --- | --- | --- | --- |
| `raw_record_id` | opaque internal identifier | required | Generated per row interpretation | unique within batch | no / yes / no |
| `batch_id` | opaque reference | required | Parent import batch | must exist | yes / yes / no |
| `sheet_alias` | string | required | Sanitized sheet alias | must exist in batch | yes / no / no |
| `row_number` | positive integer | required | XLSX row position | positive; preserve exactly | yes / yes / no |
| `raw_cells` | ordered cell map | required | Neutral openpyxl-adapter values, types, date flags, number formats, and formula flags; all populated worksheet columns are retained | no silent coercion; sensitive | yes / no / no |
| `row_class` | enum | required | movement_candidate, metadata, header, blank, auxiliary | stable classifier | yes / no / no |
| `parse_outcome` | enum | required | `PARSED`, `IGNORED`, or `REJECTED` | exactly one explicit outcome | yes / no / no |
| `error_codes` | list of enum | required | Machine-readable reasons and warnings | use defined codes only | yes / no / no |

The parser also retains `worksheet_name`, `worksheet_ordinal`, and
`row_number`. `S1:row:<number>` is a convenience identifier only; provenance
remains workbook-local until a future artifact/import-batch boundary exists.

### Parsing and validation result

The parser returns a batch result plus one result per `RawRecord`. A result must
be deterministic for the same artifact bytes and parser version.

Every extracted row has exactly one explicit outcome:

| Outcome | Meaning | Examples |
| --- | --- | --- |
| `PARSED` | The row is structurally recognized as a Santander financial movement and can be interpreted unambiguously | valid date, exactly one valid debit/credit amount |
| `IGNORED` | The row is recognized and deliberately excluded from financial movements | metadata, header, repeated header, separator, blank, known auxiliary/footer row |
| `REJECTED` | The row appears relevant to movements but cannot be interpreted safely | invalid date, missing amount, malformed amount, both debit and credit populated, ambiguous year |

`IGNORED` is not a failed parse and `REJECTED` is not silently converted to an
empty result. The parser returns a typed row result for each row in the
recognized worksheet; workbook-level structural failures use typed exceptions.

#### Auxiliary commission-summary sections

The source inspection found a primary movement-detail section followed by an
auxiliary commission-summary section in the private Santander samples. This is
an observed source structure, not a claim that every Santander export uses the
same labels or placement. The auxiliary section may contain financial-looking
rows that repeat movements represented in the primary detail.

The parser contract decision is structural: once a commission-summary section
has been recognized, financial-looking rows within that section are intentionally
`IGNORED` with a structural reason such as `commission_summary`. They do not
produce `NormalizedMovement` values and do not participate in reconciliation.
This is section interpretation, not transaction deduplication; genuinely
distinct movements with identical values must remain distinguishable by their
source section.

The validated implementation recognizes the exact normalized source markers
`resumendecomisiones` in standalone column C and `mensajes` in standalone
column A, tracks the commission-summary state, and applies this rule before
ordinary movement interpretation. The asterisk separator is treated as
auxiliary content inside the section, not as its primary boundary.

#### Debit/credit invariant

For a `PARSED` movement, exactly one of Santander's debit/cargo or
credit/abono cells must contain a valid amount:

- debit/cargo only → negative `signed_amount`;
- credit/abono only → positive `signed_amount`;
- both populated → `REJECTED` with `debit_credit_conflict`;
- both empty → `REJECTED` with `amount_missing` when the row has movement
  shape, otherwise `IGNORED` as auxiliary content.

The importer must never create a movement by calculating `credit - debit` when
both source columns are populated. Empty cells are not inferred zeroes.

#### Movement year derivation

Movement dates omit the year. Given a trusted statement period, the parser:

1. constructs every valid full date for the source day/month in the years
   covered by the period;
2. keeps only dates inside the inclusive statement period;
3. accepts exactly one result;
4. returns `REJECTED` with `date_invalid` when the day/month is impossible, or
   `date_year_ambiguous` when zero or multiple valid in-period dates remain.

This supports periods crossing December and January. It does not replace the
movement year naively from the statement start year.

For a candidate movement, validation must establish:

- a valid day/month source date and an unambiguous period year;
- exactly one debit or credit amount;
- exact decimal parsing with the observed separators and cell types;
- a non-empty description only when the source provides one; no invented text;
- currency and account identity may remain unknown at this parser boundary;
  they are populated only from trusted caller context;
- an optional running balance that is either valid or reported as a row-level
  warning when absent.

### NormalizedMovement

This is the minimum future parser output. It is not yet a persistence model.

| Field | Logical type | Required | Semantics and provenance | Normalization and validation | Synthetic example |
| --- | --- | --- | --- | --- | --- |
| `source_record_id` | opaque reference | yes | Links to immutable interpretation | must exist; supports traceability and idempotency | `raw-0001` |
| `account_ref` | sensitive opaque reference | optional at parser boundary; required before persistence | Account to which the signed effect applies | use a stable internal reference when supplied; never expose source account number | `acct-synthetic-checking` |
| `occurrence_date` | date | yes | Movement date resolved from source day/month plus period context | reject impossible or ambiguous dates | `2026-01-05` |
| `posted_date` | date | no | Not separately provided in the observed table | remain null unless a later source proves it | `null` |
| `description` | string | no | Normalized form of source column C | trim only deterministic whitespace; preserve source in raw | `Synthetic market purchase` |
| `source_reference` | string | no | Normalized copy of source column D when present | do not assume global uniqueness | `SYN-REF-002` |
| `signed_amount` | exact decimal | yes | Account effect: debit negative, credit positive | exactly one source side; no binary floating point | `-1000.00` |
| `currency` | ISO-like currency code | optional at parser boundary; required before persistence | Account currency from trusted caller context | keep unknown; do not infer from `$` alone | `CLP` |
| `running_balance` | exact decimal | no | Source column G when parseable | preserve as optional reconciliation evidence | `101500.00` |
| `movement_type` | enum | no | Future classification, not supplied by this parser | null at parse time unless a later explicit source field is confirmed | `null` |

The normalized output does not contain user corrections. A later correction must
create a new auditable representation while retaining the parser result.

## Error and row-result classification

The initial result vocabulary is intentionally small:

| Result | Meaning | Examples | Batch effect |
| --- | --- | --- | --- |
| `PARSED` | Valid movement emitted | one valid date and exactly one valid amount | continue |
| `IGNORED` | Known non-movement row | metadata, header, blank, auxiliary/note row | continue |
| `REJECTED` | Candidate row cannot be interpreted safely | invalid date, missing amount, both amount columns, malformed amount | continue; count and retain raw row |
| `fatal_file_error` | Artifact cannot be safely interpreted | malformed XLSX, no visible sheet, movement header not found, unrecoverable encoding/structure error | stop batch |

Stable initial error codes:

- `xlsx_invalid`
- `movement_header_not_found`
- `ambiguous_statement_worksheets`
- `period_context_missing`
- `period_context_invalid`
- `period_context_ambiguous`
- `date_invalid`
- `date_outside_period`
- `date_unsupported`
- `date_year_ambiguous`
- `amount_missing`
- `amount_invalid`
- `negative_source_amount`
- `zero_amount_unsupported`
- `debit_credit_conflict`
- `formula_unsupported`
- `running_balance_invalid`
- `commission_summary` (structural ignore reason for a recognized auxiliary
  commission-summary row)

`running_balance_invalid` is a row warning when the movement itself is valid;
it does not invalidate the movement because the running balance is optional.
Formula-backed movement cells are rejected rather than interpreted from cached
values. Formula-backed period metadata is a workbook-level failure because a
trusted period cannot be derived.

## Worksheet recognition and fail-closed behavior

The parser inspects visible worksheets for the fixed observed Santander header
structure: date in A, description in C, debit/cargo in E, credit/abono in F,
and balance in G. Longer E/F banking labels are accepted only when they contain
the documented `cargo`/`abono` terms. The auxiliary B and reference D columns
remain fixed but do not determine description normalization. A description in B
is unsupported and fails closed. The parser does not use the active worksheet
as the selection rule.

- exactly one structurally recognizable worksheet → parse it;
- no recognizable worksheet → raise `movement_header_not_found`;
- multiple recognizable worksheets → raise
  `ambiguous_statement_worksheets`;
- hidden worksheets are not selected automatically.

Malformed XLSX structure, missing period metadata, unsupported headers, and
ambiguous interpretation fail explicitly. The parser does not make best-effort
financial transformations.

## Monetary representation policy

The parser uses `Decimal` for every normalized amount and does not use binary
floating-point arithmetic. Supported source representations are:

- openpyxl numeric cells, converted through their textual numeric value;
- text integers;
- text amounts with a leading `$` marker;
- source-style thousands grouping with three-digit groups;
- decimal text with one or two fractional digits;
- mixed grouping/decimal separators only when grouping and fractional lengths
  are unambiguous.

Malformed or ambiguous text is rejected. Source debit/cargo and credit/abono
values must be nonnegative magnitudes. Negative source values are rejected and
never passed through `abs()` or double-negated. A zero movement amount is
rejected as `zero_amount_unsupported` because the inspected evidence does not
establish zero-value movements as meaningful transactions. Zero balances are
allowed.

## Reconciliation status

Parsing validity and reconciliation are separate. A structurally valid workbook
may produce `PARSED` movements while reconciliation remains unresolved.

The parser reports one of these statuses independently:

| Status | Meaning |
| --- | --- |
| `RECONCILED` | Opening and ending balances exist, all movement-shaped rows were parsed, and `ending_balance = opening_balance + sum(signed_movements)` |
| `NOT_RECONCILED` | Required evidence is complete, all movement-shaped rows were interpreted, and the arithmetic differs |
| `INSUFFICIENT_DATA` | Evidence is incomplete or uncertain, including a rejected movement-shaped row or missing opening/ending balance |
| `NOT_APPLICABLE` | No movement-shaped rows exist to reconcile |

Reconciliation failure or insufficient information does not invalidate an
otherwise `PARSED` movement. It remains a separate batch result.

Financial-looking rows ignored because they belong to a recognized auxiliary
commission-summary section are excluded before reconciliation; they are not
rejected evidence and cannot make an otherwise reconcilable primary detail
section fail reconciliation.

## Date and formula policy

Day/month text dates are resolved by generating all plausible full dates in the
inclusive statement period and accepting exactly one. This supports
December→January periods and rejects invalid or ambiguous long-period dates.

Full text dates and Excel `date`/`datetime` cells are accepted only when their
full date falls inside the trusted statement period. Numeric date serials that
openpyxl does not decode as a date, formula-backed dates, and unsupported date
objects are rejected. The workbook is loaded with `data_only=False`, so cached
formula values are never silently treated as source facts.
